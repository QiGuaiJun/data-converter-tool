# 数据导表工具 · 模块独立架构重构设计（v2 定稿）

> 版本：v2（2026-09-08，已按用户三项决策修订）
> 性质：设计文档（未改任何代码）。经确认后按第 8 节分批实施。
> 触发背景：用户误删"作业"连带删除了导入任务本体，暴露"各模块共享 `_jobs` 表、删除无保护"的结构性缺陷。

---

## 0. 用户决策（v1 → v2 修订依据）

| # | 待确认问题 | 用户决策 | 对设计的影响 |
|---|---|---|---|
| 1 | 删除导入任务时源文件副本是否一并清理 | **一并删除**（下次创建任务时重新关联本机文件即可） | 删除语义：删 `import_tasks` 行 + 删对应源文件 |
| 2 | 批量/目录导入是否在 v1 范围 | **先只支持单个文件** | v1 不含"任务=目录多文件"；目录选择保留为手动导入用，不作为任务形态 |
| 3 | 作业与任务的关联方式 | **作业不引用其他任务**；作业步骤配置可通过**一键复制任务配置为快照**生成（一次性复制，之后与任务无运行时关联），"一切由我重建" | 推翻 v1「P2 编排只存引用 / 运行时读任务最新配置」；产品建议 B 的 `importJobId` 运行时引用**废弃**，改为"复制快照"助手 |
| 4 | "复制配置"的具体语义 | **完整复刻原任务的全部配置选项**（复制后默认与源任务逐项一致：导入模式=追加则作业里就是追加，字段映射/类型识别/清洗规则/导入前后 SQL 等全部照搬），仅作为作业步骤的**初始配置**，之后可在作业里手动微调 | "复制"=全量拷贝 config（JSON 深拷贝），不是只拷 path/表名三件套；杜绝"作业跑出来和任务不一致"的走样 |

**由此确立的目标模型一句话**：任务（导入/导出）与作业（多步编排）是**两类互不关联的独立资产**——作业里的每一步自带完整配置快照（可从任务"完整复刻"生成，复制后与任务彻底脱钩）；删除任务只删任务及源文件，删除作业只删作业。

## 1. 目标与原则

**目标**：让每个业务模块都是**独立资产**，互不牵连；删除任一资产不影响其他资产，也不存在"被引用而悬空"的状态。

| 原则 | 说明 |
|---|---|
| P1 一物一表 | 导入任务 / 导出任务 / 作业编排 / 保存查询 / 定时调度，各自独立存储 |
| P2 作业自包含 | 作业步骤**内嵌完整配置快照**（含字段映射/类型/清洗/SQL/格式），无任何对任务的运行时引用；复制配置 = 一次性拷贝，之后与源任务无关 |
| P3 删除即彻底 | 删导入任务 = 删记录 + 删其源文件（含 linked_sources 副本）；删作业 = 只删作业记录；互不影响 |
| P4 向后兼容 | 执行链路（导入→库、导出→文件、日志、定时触发）不动，只改配置存储与来源；历史作业/调度迁移后行为不变 |
| P5 助手而非耦合 | 提供"从任务复制配置到作业步骤"的 UI 助手，省去手填，但**不建立任何 id 引用** |

## 2. 现状问题诊断

**现状**：`_jobs` 一张表承载了所有"类作业"实体，前端（导入页 / 作业页 / 定时页）都读它并按启发式区分，导致：

| 问题 | 表现 |
|---|---|
| 资产混同 | 导入任务 = "单 import 步骤的 job"，显示在作业页列表；用户删"作业"即删任务本体 |
| 运行期引用（v1 已引入，v2 废弃） | 多步作业的 import 步骤用 `config.importJobId` **运行时**读被引用任务的最新配置 → 任务一删，作业悬空报错（用户实际踩坑） |
| 删除无保护 | 前端 DELETE 直接按 id 删 `_jobs`，无"这是导入任务"提示，也无源文件清理 |
| 命名/去重混乱 | 同一业务（中秋试饮活动）存在多个同名 job（单步导入、导出、自动作业、全链路），难管理 |

**数据形态快照（2026-09-08）**：

| 现状实体 | 数量 | 落点 |
|---|---|---|
| 纯导入任务（单 import 步骤、自含 config） | 4（小票导入/中秋试饮权益/云购商城/Bug2） | `_jobs` |
| 纯导出作业（单 export 步骤、内嵌 items SQL） | 1（中秋试饮活动） | `_jobs` |
| 保存查询 | 1（中秋试饮活动大 SQL） | `_saved_queries`（已是独立资产 ✅） |
| 查询型 job（单 query 步骤→queryId） | 1（查询：中秋试饮活动） | `_jobs` |
| 自动作业（单 job 嵌套步骤→jobId） | 3 | `_jobs` |
| 多步作业（importJobId 引用 + export 内嵌） | 1（中秋试饮活动全链路） | `_jobs` |

## 3. 目标数据模型（新增表，不删旧表）

> 策略：**新表并行** + 迁移，旧 `_jobs` 保留为"历史归档/兜底"，避免一次性破坏。

### 3.1 资产表

```sql
-- A1 导入任务资产（原：单 import 步骤 job 的 config 整体搬移）
CREATE TABLE IF NOT EXISTS import_tasks (
  id TEXT PRIMARY KEY,             -- 保留原 job id，调度/日志引用不断
  name TEXT NOT NULL,
  source_path TEXT NOT NULL,       -- 服务器可读真实路径（含 linked_sources 副本路径）
  connection_id TEXT DEFAULT '',   -- 目标库连接（空=本地 sqlite）
  config_json TEXT NOT NULL,       -- 完整导入配置（字段映射/类型/清洗/导入前后 SQL/模式…）
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- A2 导出任务资产（原：单 export 步骤的 config 搬移）
CREATE TABLE IF NOT EXISTS export_tasks (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  config_json TEXT NOT NULL,       -- items(SQL/表/查询引用)+格式+文件名规则…
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- A3 保存查询（已存在 _saved_queries，沿用，不改结构）
```

### 3.2 作业表（自包含编排）

```sql
CREATE TABLE IF NOT EXISTS jobs (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  steps_json TEXT NOT NULL DEFAULT '[]',   -- 每步内嵌完整配置快照
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- 步骤结构（steps_json 内一项）：与现状步骤结构完全一致，只是 config 必为完整快照
-- { "id":"s1", "name":"导入小票", "type":"import"|"export"|"query"|"job",
--   "enabled":true, "continueOnError":false,
--   "config":{ /* 完整配置：字段映射/类型/清洗/导入前后SQL/SQL/文件名… */ } }
--
-- ⚠️ 禁止出现 config.importJobId / config.jobId 这类运行时引用键（迁移时烘焙成快照）
```

### 3.3 调度表

```sql
-- schedules：job_id 泛化为"目标引用"（兼容现状 + 支持直达单任务）
ALTER TABLE _schedules ADD COLUMN target_kind TEXT NOT NULL DEFAULT 'job';
-- target_kind: 'job' | 'import_task' | 'export_task'
-- 迁移规则：现 job_id 指向"将被拆为单任务"的 → target_kind='import_task'/'export_task'；
--           指向多步作业的 → target_kind='job'（jobs.id）
```

### 3.4 依赖关系图

```
导入任务(import_tasks)  ──独立──┐
导出任务(export_tasks)  ──独立──┤（可被作业"复制快照"，复制后无关联）
保存查询(_saved_queries)──独立──┤
作业(jobs，步骤=自包含快照)     ┘   <── 触发 ── 调度(schedules)
删除规则：
  删任务 → 删记录 + 删其源文件副本；不影响任何作业
  删作业 → 只删 jobs 记录；不影响任何任务
  （因无运行时引用，不存在"悬空引用"状态；页面也不再有"被引用"纠缠）
```

## 4. 存量迁移方案

> 迁移脚本独立、幂等、可回滚（迁移前先备份 `imports.db`）。迁移**只复制/改写，不删旧 `_jobs` 行**（旧表保留为只读归档）。

| 现状 | 迁移到 | 规则 |
|---|---|---|
| `_jobs` 单 import 步骤（任务语义） | `import_tasks` 一行 | 保留原 job id；`source_path=config.path`、`connection_id=config.connectionId`、`config_json=config` |
| `_jobs` 单 export 步骤（任务语义） | `export_tasks` 一行 | `config_json=config`（含 items） |
| `_jobs` 多步 / 嵌套作业 | `jobs` 一行（步骤改写） | **烘焙引用为快照**：import 步含 `config.importJobId` → 查被引用任务，把其完整 config 复制为该步 config（去除 importJobId 键）；job 嵌套步含 `config.jobId` → 递归展开或复制被嵌套作业为内联步骤；export/query 步 config 原样保留 |
| `_jobs` 单 query 步骤（查询型 job） | `jobs` 一行 | config 保留（queryId 指向 _saved_queries 属正常引用——查询本就是独立资产，保持） |
| `_saved_queries` | 不动 | 已是独立资产 |
| `_schedules` | 原地加 `target_kind` | 按上面 3.3 规则归类；`job_id` 值不变 |

**迁移产物核对**：迁移后每个旧作业/任务的"可执行内容"逐格等价；多步作业迁移后跑一次与迁移前结果一致（14:42 全链路基线对比：导入小票 + 中秋试饮 27 行 + 导出文件）。

## 5. 后端 API 设计（新增/调整）

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/import-tasks` | GET / POST / DELETE | 导入任务资产 CRUD |
| `/api/export-tasks` | GET / POST / DELETE | 导出任务资产 CRUD |
| `/api/jobs` | GET / POST / DELETE | 多步作业 CRUD；POST 时校验每步 config 无运行时引用键 |
| `/api/import-tasks/:id/source` | GET | 返回任务源文件信息（删除确认页展示用） |
| `/api/import-tasks/:id` DELETE | — | 删记录 + **删源文件**：若 source_path 落在 `linked_sources/`（或 `task_sources/` 残留副本）则删文件；真实路径（用户自填）**不删**（可能被别人/业务用） |
| 调度执行 | — | 按 `target_kind` 路由：import_task → 用 import_tasks 行执行导入；export_task → export_tasks；job → jobs 多步 |

执行器（`run_saved_job` 等）改为：作业步骤 config 即完整快照 → 直接交给现有 `execute_import_step` / `run_export_job` / `execute_query_step`（**不再有 importJobId 解析分支**，删除 `resolve_import_step_config` 相关逻辑或保留为兼容但标记废弃）。**导入/导出/查询内核不变**。

## 6. 前端改造点

| 页面 | 改动 |
|---|---|
| 导入页（IN） | 任务列表读 `/api/import-tasks`；"保存为任务"写 `import_tasks`；任务删除加二次确认弹窗："将同时删除服务器上的源文件副本，是否继续？" |
| 导出/查询页 | 保存的导出任务写 `export_tasks`；保存查询沿用 `_saved_queries` |
| 作业页（JOB） | 列表只显示多步 `jobs`（导入任务不再混入）；步骤编辑器去掉"引用导入任务"下拉，改为"**从导入任务复制配置**"按钮：选任务 → **完整复刻其全部配置**（深拷贝 config，导入模式/字段映射/类型/清洗/前后 SQL 逐项与源任务一致）进当前步骤 → 提示"已复制为独立快照，与该任务不再关联，可在作业内手动微调"；删除作业无任何牵连提示 |
| 定时页 | 目标类型明确显示（作业 / 导入任务 / 导出任务），显示名称而非裸 id |
| 全局 | 列表项类型徽标（导入任务/导出任务/作业）；危险删除（删任务带源文件）用强警告模态 |

## 7. 删除保护规则（v2 简化版）

1. **删导入任务**：二次确认（"将删除源文件副本"）→ 删 `import_tasks` 行 + 删 `linked_sources`/`task_sources` 下对应副本文件。**不影响任何作业**（作业持有自己的快照）。
2. **删作业**：只删 `jobs` 行。**不影响任何任务**。
3. **删调度**：只删 `_schedules`。不影响任务与作业。
4. 删除后若文件已被别的任务/作业的路径引用（如多个任务指向同一 linked_sources 文件）：**先检查文件引用计数**，仅当无其他任务指向时才删文件；否则仅删记录并提示"文件仍被其他任务使用，已保留"。
5. 因作业自包含，不存在"删除导致他人悬空"——**不引入引用完整性检查**，逻辑最简。

## 9. 风险与兼容

- **最大风险**：批次 2 迁移遗漏 → 资产"看不见"。缓解：迁移前备份、迁移脚本幂等 + 产物数量核对、旧 `_jobs` 保留只读兜底可随时对照回滚。
- **源文件误删风险**（决策 1）：删除任务的二次确认 + 引用计数（4 条规则）双重保护；真实路径（用户自填目录）一律不删。
- **产品建议 B 弃用代价**：已上线的"引用导入任务"运行时引用将停用。当前"中秋试饮活动全链路"类作业靠批次 2 烘焙成快照保住可执行性，无需用户重建；之后新建作业用复制助手。
- 执行器只改"配置来源/引用解析"，不碰导入/导出/查询内核 → 回归面小。
- 单文件范围（决策 2）：目录批量任务不建；现有手动导入的"选择目录"能力保留。
