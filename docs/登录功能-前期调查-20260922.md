## 一、结论摘要（先说三件最重要的事）

1. **项目已经有认证，不是从零开始。** 现有实现是 HTTP Basic Auth：环境变量开关 + 单账号 + 浏览器原生弹窗，
   代码在 `server.py:6295-6319`（校验）与 `server.py:6375-6387`（拦截）。它默认**只在公网部署时启用**，
   本机启动是关的（`desktop_launcher.py:61` 显式 `APP_AUTH_ENABLED=false`）。
2. **缺的不是"认证"而是"登录体验 + 账号体系"**：没有登录页、没有用户表、没有会话、没有登出、
   没有审计。你现在想要的"登录功能"，本质是把现有的单账号 Basic Auth 升级成正经的登录模块。
3. **要不要做、做到哪一档，取决于一个还没确认的事实：谁会访问这个工具。**
   本机单人用 → 保持现状即可；局域网/公网多人用 → 必须做，而且**优先级很高**——
   因为 2026-09-21 查询模块已放开写权限（等于能 `DROP` 表），而连接账号是 `root`，
   现在"能打开页面"就等于"能删生产库"。

### 2.4 风险面变化（为什么现在提这件事）

* 2026-09-21 提交 `84012a9` 把查询模块升级为**完整 SQL 控制台**：可执行 `DROP` / `TRUNCATE` / `DELETE` /

## 三、需求确认（请你逐条拍板）

> 下面 6 个问题的答案会直接决定架构，建议按顺序回答；每个都给了我的推荐与理由。

**Q1. 谁会访问？（最关键）**

| 选项 | 含义 | 我的判断 |
|---|---|---|
| A. 只有我，本机用 | 登录只是"防同事顺手点开" | 级别最低，可只加一个简单的口令页 |
| B. 少数同事，通过局域网访问这台机器 | 需要多账号 + 至少能区分"谁" | **需要做**，推荐档位 B |
| C. 部署到云上，外部/多市场同事访问 | 必须真正的账号体系 + 传输加密 | **必须做**，且要 HTTPS + 审计 |

**Q2. 账号体系**：单账号够用，还是要"每人一个账号 + 角色"？
　→ 推荐：**每人一个账号**。理由：多账号才能追责；共用账号在有 root 写权限的场景下等于没有审计。

**Q3. 登录方式**：账号密码表单（推荐）/ 保留浏览器 Basic 弹窗（省事但无法登出）/ 免密（IP 白名单、邀请码）？
　→ 推荐：**账号密码表单 + Cookie 会话**，Basic 保留为兜底（供脚本/健康检查用）。

**Q4. 会话策略**：多久失效？关闭浏览器是否登出？要不要"记住我"？
　→ 推荐：**默认 8 小时 / 关闭浏览器失效**；"记住我"可选 7 天。当前服务重启频繁（每天关窗口），要明确"重启即全员下线"是否可接受。

**Q5. 权限粒度**：登录后一律全权，还是要分级？
　→ 推荐分级：`admin`（全部）/ `operator`（导入、导出、查询读写）/ `viewer`（只读查询）。
　理由：查询模块现在能 `DROP` 表，**至少要把"能写"和"只能看"分开**。

**Q6. 审计**：要不要记录"谁在什么时候执行了什么 SQL / 导入了什么文件 / 改了哪条连接"？
　→ 推荐：**要**。这是多账号相对单账号的最大收益，也是出事时唯一的追溯手段。

## 四、方案选型（三档，按你的 Q1 选择）

### 档位 A｜极简：口令页 + 单账号会话
* 新建 `public/login.html`，服务端加 `/api/auth/login` `/logout` `/me` + 签名 Cookie。
* 密码仍取 `ADMIN_PASSWORD`（或首次启动生成并打印到控制台）。
* **不**建用户表、**不**做权限、**不**做审计。
* 适合 Q1=A。改动集中在 `server.py` 的 `require_auth`（换成 Cookie 校验）+ 一个登录页 + `shell.js` 加 401 跳转。

### 档位 B｜多用户 + 角色 + 审计（**推荐**）
新增三张表（沿用现有 `create table if not exists` 风格）：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `_users` | `id, username, password_hash, role, enabled, created_at, last_login_at` | 密码用 `hashlib.scrypt`/`pbkdf2` 加盐哈希，**不存明文** |
| `_sessions` | `id, token_hash, user_id, created_at, expires_at, ip, user_agent` | 只存 token 的哈希；支持"强制下线" |
| `_audit_logs` | `id, user_id, action, target, detail, created_at` | 记录查询执行（含 SQL 摘要与危险等级）、导入导出、连接增删改、用户管理 |

配套功能：登录页、顶栏"当前用户 + 登出"、改密、管理员建/停用账号、首次启动引导创建管理员、
401 统一跳登录、按角色的前端隐藏与后端二次校验。

### 档位 C｜对接外部身份（企业微信 / 飞书扫码 / LDAP）
* 仅当"公司内网 + 有企微或飞书组织"时才值得。
* 前提条件较多：企业应用凭据、回调域名（`127.0.0.1` 走不通扫码登录）、HTTPS。
* 结论：**现阶段不建议**，先把 B 做出来；C 可作为后续增强（保留 `_users` 作为映射表）。

## 五、影响面清单（改一处会牵动哪里）

| 影响对象 | 具体影响 | 处理方式 |
|---|---|---|
| **验收复跑套件（最容易被忽略）** | `acceptance/` 下 13 个 Playwright / API 脚本全部直连 HTTP，一旦强制登录会**全线 401** | 提供"测试凭据"或独立豁免令牌（仅沙箱用），并同步改脚本 |
| 健康检查 | Railway/Render 用 `/api/ping` 探活，必须保持免认证 | 沿用现有豁免，不要扩大 |
| 定时任务 / 作业 | 后台线程执行，不走 HTTP，**不受登录影响**；但"谁创建的"目前无处记录 | 若做审计，需给 `_jobs` / `_schedules` 补 `created_by` |
| 导出文件下载 | 走 `/download?path=`，Cookie 同源可用 | 若将来要做"分享链接"，需签名 URL 机制 |
| CSRF | Cookie 认证下浏览器自动带凭据，而查询页现在能 `DROP` 表 | `SameSite=Lax/Strict` + 自定义头校验（或 CSRF token） |
| 前端 11 个页面 | 都要加"用户区 + 登出"，401 要能统一跳登录 | 统一放在已全站引用的 `public/shell.js`，避免重复改 11 处 |
| 本机使用习惯 | 现在双击 bat 打开即用；加登录后多一步 | **建议本机保留免登录**（沿用 `APP_AUTH_ENABLED=false`），只在多人/公网场景启用 |
| 部署配置 | `render.yaml` 的 `ADMIN_PASSWORD` 语义会变 | 改为"仅用于首次引导创建管理员"，之后由页面管理 |

## 六、风险与"不做"的后果

* **不做的后果**：只要服务被第二个人访问到（局域网、远程桌面、云部署），就存在"无痕删除生产库"的可能；
  当前查询模块 + root 账号的组合让这个风险从"理论"变成"点两下鼠标"。
* **做的风险**：认证是单点，实现有漏洞则等于没有；会话机制若落库要考虑过期清理与并发；
  测试脚本改造若有遗漏会导致验收链断裂（已列入影响面清单）。
* **必须守住的边界**：密码一律哈希存储；会话 token 只存哈希；Cookie `HttpOnly` + `SameSite`；
  公网部署必须 HTTPS；危险操作（`DROP`/`TRUNCATE`/无 WHERE 的删改）在登录之上**继续保留**现有令牌确认。
