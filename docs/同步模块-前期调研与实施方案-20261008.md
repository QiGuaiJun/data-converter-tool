## 一、结论先行

1. **"同步"不是新需求，而是一个预留了约半年、一直没实现的占位模块。**
   后端有 3 处硬拦截、定时任务对话框里有个灰掉的「同步」单选框、导航栏有个点开只有一张说明卡的页面——都是它。

2. **设计意图早就写在代码里**（`public/module-pages.js:3` 原文）：
   > 配置**数据库到数据库**同步任务，包含**源库、目标库、字段映射、同步模式和执行日志**。

3. **家底比预想的厚。** "字段映射""同步模式"这两块通常最费工的东西，导入模块里已有现成实现：
   四种写入模式（追加 / 更新 / 覆盖 / 重建）、按名称 / 按顺序 / 自定义的列匹配、
   **按匹配键 upsert**（`target_update_rows` 已返回 inserted/updated 两个计数）、
   目标表不存在时自动按源数据建表、字符列自动拓宽。
   **一期工作量的大头不在算法，而在"从 MySQL 读数据"这条新链路**——现有代码只会读 Excel。

4. **最大的真缺口是"增量"。** 现有断点是**行偏移**（`_import_checkpoints.rows_done`），
   没有"上次同步到哪个时间戳 / 哪个自增 ID"的**水位线**概念。增量同步必须从零做。

5. **范围已定（业主 2026-10-08）**：**A + B** —— 库→库整表同步（含源端可写 SQL）；
   三档模式（全量覆盖 / 按主键 upsert / 按时间戳增量）；既能单独跑，也能当作业与定时任务的子任务。

6. ⚠️ **【重要】实测后推翻了"用时间戳做增量"这个默认**（详见 §2.4）：
   用本机 `lcdp_fe` 副本查了真实表结构（**未碰生产库**）——
   ① 全库**没有任何** `ON UPDATE` 列，也没有"更新时间/修改时间"这类列 → **"哪一行被改过"库里没有记录**；
   ② 核心表**没有主键、没有唯一索引**，且 `会员小票表.提单编号` **不唯一**（一行一商品）；
   ③ 有"会变的列"（`订单状态` / `商品退款状态`），而变动发生在**任意年龄**的行上
   —— 实测有售后状态的最早一行创建于 **2022-09-01（1,498 天前）**；
   ④ 部分"时间"列是**字符串**且只到"天"（`提单时间` varchar(100)，值形如 `2025-01-30`）。
   **结论：时间戳增量对你现有这些表买不到任何东西**（滚动窗口要开到 4 年才不漏 = 全表）；
   **但全量覆盖完全跑得动**（最大表 30 万行 / 173 MB，现有 `LOAD DATA LOCAL INFILE` 是秒级），
   而且结果是确定的"目标 = 源"。**建议现有核心表一律用全量覆盖。**

## 1.5 "同步"到底在同步什么（先把概念说清）

> 业主反馈"还不清楚同步的对象是什么意思、分别的实现场景是什么"。这一节专门讲这个。

### 这个工具总共只有四条数据链路，**只有一条是空的**

| 从 \ 到 | → MySQL 数据库 | → Excel 文件 |
|---|---|---|
| **从 Excel 文件** | **导入**（已实现） | 不适用（文件之间没有同步概念） |
| **从 MySQL 数据库** | **同步**（待开发） | **导出**（已实现） |

- **导入** = 文件 → 库（把 Excel 灌进 MySQL，有字段匹配、重复表策略、断点续传）
- **导出** = 库 → 文件（把 MySQL 导成 xlsx/csv/txt/json/xml，支持多表与多段 SQL）
- **查询** = 只看不写（SQL 控制台）
- **同步** = **库 → 库** ← **缺的就是这一条**

所以"同步"不是凭空加功能，而是**补上唯一缺失的那条链路**（这也正是 `module-pages.js` 里那句
"配置数据库到数据库同步任务"的意思）。

### "对象"和"方向"指什么

一条同步任务只有三个部分，方向**永远单向**（源端只读、不写，只写目标端）：

1. **源端**：数据从哪个连接的哪张表来
2. **中间**：字段怎么对应（列名可能不一样）、本次要同步哪些行（同步模式 + 增量条件）
3. **目标端**：数据写到哪个连接的哪张表去

例：把生产库 `192.168.7.173/lcdp_fe` 的 **会员小票表** 每天搬一份到分析库——
因为生产库是只读的、不能在上面跑分析查询，所以在另一台库留一份副本。

### 三档范围分别是什么场景

**第一档 · 库 → 库，整表同步（建议：必做，一期的核心）**

- 场景：生产库只读不能跑分析 → 把「会员小票表」每天增量搬到分析库；
  或把云购商城的销售数据从业务库搬到报表库。
- 配置方式：选源连接 → 选源表 → 选目标连接 → 选目标表 → 选模式。**全下拉，不写代码。**

**第二档 · 源端可写 SQL（建议：二期）**

- 场景 A「只同步一部分」：例如只同步中秋试饮活动的小票 → `where 活动编码 = 'xxx'`
- 场景 B「先关联再同步」：例如小票表 join 会员表，同步成一张宽表过去，那边拿到就能直接用
- 场景 C「列做加工」：只取几列、改列名、金额单位换算
- 代价：源端不再是"一张表"而是"一段 SQL"，于是**主键探测和增量水位都得让用户自己指定**，
  配置复杂度和配错概率都上一个台阶。**建议一期先不做，等第一档跑顺了再加。**

**第三档 · MySQL ↔ Excel（建议：不做）**

- "导出报表给同事看" —— 这已经是**导出模块**在做的事（支持 xlsx/csv/txt/json/xml、多表、多段 SQL）
- "Excel 进库" —— 这已经是**导入模块**在做的事（字段匹配、重复表策略、断点续传、自动扩列）
- 如果同步再做一遍，同一个需求就有两个入口，将来改一处忘一处 →
  **这是维护负担，不是新能力。** 建议明确不做。

### 一句话总结

**同步 = 库到库的表级数据搬运。** 一期做第一档（含三种模式），第二档留作二期，
第三档与现有模块重叠、建议永不做。

### 2.4 对真实库的实测（**重要：推翻了一项原推荐**）

业主说"当前不清楚具体实现什么"，所以我直接去查了真实表结构。
**没有碰生产库**——本机 3306 上有一份 `lcdp_fe` 的完整副本（会员小票表 30 万行、
云购商城销售数据表 10 万行都在），全部查询都是只读。

### 发现 1：全库不存在"行最后修改时间"

```sql
select table_name, column_name from information_schema.columns
where table_schema='lcdp_fe' and extra like '%on update%';
-- 结果：0 行
```

同时也没有任何名字像 `更新时间 / 修改时间 / update_time / gmt_modified` 的列。
**含义**：时间戳增量缺少它最该用的那一列——"哪一行被改过"在库里根本没有记录。

### 发现 2：核心表没有主键、也没有唯一索引

会员小票表 / 云购商城销售数据表 / 中秋试饮 / 领航部-权益核销明细
**全部只有普通索引**（`non_unique=1`）。

**含义**：按主键 upsert 无键可用，只能让用户手工指定**业务键**；
而且工具必须先做唯一性检测——实测 `会员小票表.提单编号` **不唯一**
（302,938 行只有 261,473 个不同提单编号）。因为它**一行一个商品**，
真实业务键是 `提单编号 + 商品编码`。

### 发现 3（致命）：会变的列存在，且变动发生在任意年龄的行上

`云购商城销售数据表` 有 `订单状态`、`商品退款状态`，都是事后变化的。实测：

| 项 | 实测值 |
|---|---|
| 有售后状态的行 | 5,000 行（退款成功全额 4,554 / 退款关闭 364 / 部分退款 82） |
| 这些行里**最早**的订单创建时间 | **2022-09-01，距今 1,498 天** |
| 退款状态实际取值 | `退款成功（全额退款）` / `退款关闭` / `退款成功（部分退款）` / NULL |

**也就是说：一笔 2022 年的订单今天退款了。** 如果水位用"订单创建时间"，
**这一行永远同步不过去**，而且全程无报错、同步记录显示"成功"。

### 发现 4：时间列有的存成字符串，而且只到"天"

| 表 | 列 | 类型 | 实测 |
|---|---|---|---|
| 会员小票表 | 提单时间 | **varchar(100)** | 值形如 `2025-01-30`，**0 行带时分秒** |
| 中秋试饮 | 核销时间 | **varchar(255)** | 字符串 |
| 领航部-权益核销明细 | 核销时间 | date | 只有天 |
| 云购商城销售数据表 | 订单创建时间 | datetime | ✅ 带时分秒（唯一可用的一列） |

### 实测汇总：这些表到底适合什么模式

| 表 | 行数 | 体积 | 主键 | 行修改时间 | 会变的列 | 推荐模式 |
|---|---|---|---|---|---|---|
| 会员小票表 | 302,938 | 173 MB | ❌ | ❌ | 状态（3 个值） | **全量覆盖** |
| 云购商城销售数据表 | 104,496 | 87 MB | ❌ | ❌ | 订单状态 / 退款状态 | **全量覆盖**（增量必漏退款） |
| 领航部-权益核销明细 | 42,707 | 8.5 MB | ❌ | ❌ | 核销时间 | 全量覆盖 |
| 中秋试饮 | 873 | 0.2 MB | ❌ | ❌ | 核销次数 | 全量覆盖 |

### 为什么"滚动窗口"也救不了

窗口越大越贵，但售后跨了 4 年：

| 窗口 | 云购商城销售数据表 | 会员小票表 |
|---|---|---|
| 最近 7 天 | 53 行 | 6,076 行 |
| 最近 30 天 | 509 行 | 14,199 行 |
| 最近 90 天 | 1,699 行 | — |
| **全表** | **104,496 行** | **302,938 行** |
| **售后最久的行** | **1,498 天前** | — |

窗口确实很划算（几百行 vs 十万行），**但要覆盖售后就得把窗口开到 1,498 天 = 全表**。
所以对这两张表，增量**买不到任何东西**。

### 好消息：全量同步完全跑得动

最大的表 302,938 行 / 173 MB。项目里已有 `mysql_load_rows()` 走
`LOAD DATA LOCAL INFILE`，30 万行是**秒级**。每天全量跑一次毫无压力，
而且结果是**确定的"目标 = 源"**，没有增量那一堆边界问题。

### 因此：决策 4 的结论要修正

**时间戳增量的代码照做**（保留给"只增不改"的表，例如纯流水日志），
**但不要用在你们现有的核心表上**——现有核心表建议一律用**全量覆盖**。

## 三、需要你拍板的 4 件事

> 下面是会**实质改变方案与工作量**的决策。每条都给了我的建议默认值，你不回我就按建议走。

### 决策 1：同步的方向与对象范围　⏳ **待业主看过 §1.5 后确认**

概念说明与各自场景见 **§1.5**。选项如下：

| 选项 | 含义 | 工作量 |
|---|---|---|
| **A（建议）** | **MySQL → MySQL，表级同步**（选源表 → 选目标表 → 选模式，全下拉不写代码） | 基准 |
| B | A + 支持"用 SQL 取源数据"（源端可写 where / join / 取列） | +30% |
| C | 还要支持 MySQL → Excel / Excel → MySQL | **与现有导入/导出模块重叠，建议不做** |
| D | 本机 ↔ 云端（多端工具元数据同步） | 与占位意图完全不同，不建议混做 |

**建议一期选 A**，B 作为二期。理由：占位页明确写的是"数据库到数据库"，
而文件那两条链路已经分别由导入/导出模块覆盖；若同步再做一遍，同一需求会有两个入口。

### 决策 2：同步模式要哪几档　✅ **已确认（2026-10-08）**

业主确认：**三档全要** —— 全量覆盖 + 按主键 upsert + 按时间戳增量。
交付顺序：全量覆盖 → 按主键 upsert → 按时间戳增量（增量最难，放最后）。

| 模式 | 语义 | 已有基础设施 |
|---|---|---|
| 全量覆盖 | 清空目标表后按源全量写入 | ✅ `importMode=overwrite` / `rebuild` |
| 按主键 upsert | 主键存在则更新，不存在则插入 | ✅ `target_update_rows()` 已实现并返回 inserted/updated |
| 按时间戳增量 | 只取源表 `update_time > 上次水位` 的行 | ❌ **需新做水位线** |

### 决策 3：同步任务怎么存　✅ **已确认（2026-10-08）**

业主确认：**独立同步任务表**。
- `_sync_tasks` 存任务配置（源/目标连接、源表、目标表、字段映射、模式、增量列）
- `_sync_watermarks` 存水位线，**与任务配置分开存**（任务被改时水位不丢）
- 作业与定时任务通过"引用一条同步任务"来调用

理由：增量水位需要一个**稳定的任务身份**来挂靠，而作业步骤没有稳定 id
（步骤可以随时增删改，水位就会跟着错位）。

### 决策 4：增量靠什么判定　✅ **已确认（2026-10-08），⚠️ 但核查后需要修正用法**

业主确认：**时间戳列**（如 `update_time` / `gmt_modified`，用户在下拉里选一列）。

**核查已完成（§2.4，用本机 `lcdp_fe` 副本，未碰生产库），结论不乐观：**

- 全库**没有任何 `ON UPDATE CURRENT_TIMESTAMP` 的列**，也没有"更新时间 / 修改时间"这类列
  → 根本没有"行最后修改时间"可用
- 核心表**没有主键**，`会员小票表.提单编号` 还**不唯一** → upsert 的键也得用户手工指定
- 有"会变的列"（订单状态 / 退款状态），且变动跨 **1,498 天**（最久的一行创建于 2022-09）
- `会员小票表.提单时间` 是 **varchar(100) 且只到"天"**；只有
  `云购商城销售数据表.订单创建时间` 是 datetime 带时分秒

**修正后的用法（建议）：**

| 场景 | 用什么 |
|---|---|
| 你们现有的核心表（会员小票表 / 云购商城销售数据表 / 权益核销） | **全量覆盖**（30 万行 / 173 MB，秒级，结果确定） |
| 将来出现的"只增不改"的流水表（有真正的 created_at 且不会回改） | 时间戳增量 |
| 目标表需要保留源端没有的行 | 按业务键 upsert（业务键由用户指定，工具先做唯一性检测） |

**时间戳增量的代码照做**，但界面上必须标注"**仅适用于只增不改的表**"，
并在用户选中一个"存在会变列"的表时给出明确警告。**不允许静默地给出不一致的数据。**

#### 六、实现时要注意（都踩过）

**面板**
- ⚠️ **新插入的节点 `data-type="new"` 必须有自己的面板**。否则会掉进 `PANELS.skip` 的兜底，
  表现为「点了 `＋` 打开的面板是分支出口说明，根本选不了类型」——本次实测踩到。
- 面板内容按类型整体重绘（`drawerBody.innerHTML = PANELS[type]`），
  切类型时先 `markGroup("type", 当前类型)` 再渲染，否则四张卡全是未选中态。

**布局**
- ⚠️ **「适应窗口」必须先留出四周边距再算缩放**：
  `availW = r.width - M*2 - (面板打开 ? 664 : 0)`，然后 `px = M + (availW - bw*scale)/2 - minX*scale`。
  少了这个边距，居中项会算成 0、`px` 变成负数，**节点直接贴到左上角被裁掉**。
- ⚠️ **关面板后要重新适应窗口**，否则画布会停在「给面板让位」的偏左位置，左边被裁。
- 面板打开时右下角三个按钮要左移（`.stage.drawer-open .flow-actions{right:648px}`），否则被面板压住。

**画布**
- 连线用 SVG 画在**同一个被 `transform` 变换的容器**里；缩放**以光标为锚点**
  （`px = cx - (cx - px) * (next / scale)`）。
- 端口支持「高度比例 `fy`」，让 `是`/`否` 两条线从同侧不同高度出发、标签上下排列。
- **图结构单独存 `NEXT`，不能只靠线性 `order`**：`order` 只管 `＋`/`−` 的定位与整体右移；
  增删节点要**接进图里**（X 的第一个后继改指新节点、新节点继承原后继；删节点时把指向它的边改指其后继）。
- **增删节点后自动「适应窗口」**；节点动态增删 → 拖动/点击一律用**事件委托**绑在 `world` 上。
- 「点空白关面板」挂 **`click`**，不要挂 `pointerup`（后者会被 `setPointerCapture` 的移动事件干扰）。

**测试写法**
- ⚠️ **判断「选项有没有露出来」不能数 DOM**：隐藏元素仍在 DOM 里，要用 `offsetParent !== null` 过滤。
- ⚠️ **点空白必须真的点「探测到的那个点」**：先 `elementFromPoint` 拿到确认是画布的点再点。
- ⚠️ Playwright 的 `click` 点元素几何中心并做命中判定，被遮挡会报 "intercepts pointer events"；
  点标题 `.n-title` 最稳。

#### 七、配置归属与一致性铁律（业主 2026-10-09 提出 · 硬要求）

> 业主原话：「每个节点下的详细配置信息必须是符合当前节点的配置，**不得与其他节点信息相违背**。」

**根因**：初版每个面板各写各的硬编码文案，没有一份共享的任务配置 —— 必然会互相违背。
实测查出 **8 处**，都有具体代码位置：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **「写入方式」写了两份**：同步模式节点说「清空目标后按源全量重写」，目标节点又有一份「清空后写入 / 直接追加」 | 在目标节点选「直接追加」，模式节点仍说「清空后全量重写」——**直接打架** |
| 2 | 「增量模式」与「清空后写入」**可以同时配出来** | 清了表还谈增量，语义崩 |
| 3 | 「执行条件」**不随模式联动**，恒定选中「水位之后有新增行才执行」 | 全量覆盖模式下**没有水位**，条件不成立 |
| 4 | 「增量设置」**任何模式下都可编辑** | 配了也不生效，用户以为配上了 |
| 5 | 水位列候选**硬编码**了「提单时间」和「订单创建时间」 | 源表是「会员小票表」，它**没有「订单创建时间」这一列** |
| 6 | **源表切换后下游全不变**：改成云购商城销售数据表（104,496 行 / 31 列）后，卡面还写 302,938 行，映射列清单与预计耗时都不动 | 卡面与实际配置不一致 |
| 7 | 「本轮跳过」节点恒定说「增量模式下…」，**不看当前模式** | 全量模式下这条分支根本不会触发却不说 |
| 8 | 「预计耗时 约 14 秒」**硬编码** | 换表后不成立 |

**三条铁律**

1. **一个配置项只有一个归属节点**，其它节点只能「只读展示」或「推导」。
   典型：**「写入方式」由「同步模式」推导** —— 目标节点只读展示它并注明"由同步模式决定"，
   不提供第二份选项。两个节点因此永远说不出不一样的话。
2. **面板里的候选值必须来自当前任务实际选中的上游对象**，不能硬编码。
   水位列 / 业务键的候选来自**当前源表真实存在的列**；换源表后全部重算。
3. **非法组合在选的那一刻就禁用或改写**，而不是允许配出一个矛盾状态。
   非增量模式 → 「增量设置」整段置灰不可编辑；非 upsert → 「业务键」置灰；
   切走增量模式 → 自动清空水位列。

**落地方式**

```
TASK（单一真值源）
   ├── cardOf(id)      → 每张节点卡面由 TASK 推导
   ├── panelHTML(type) → 每个面板由 TASK 推导（候选值、置灰、只读块都在这里算）
   ├── repaintAll()    → 一处改了 TASK，所有节点卡面重算
   └── checkConsistency() → 兜底自检，暴露为 window.__taskConsistency()
```

**「模式」与「写入方式」的推导表**（目标节点只读展示这里算出来的值）

| 同步模式 | 同步范围（模式节点展示） | 写入方式（目标节点只读展示） |
|---|---|---|
| 全量覆盖 | 源表全量 | 清空后写入（先 delete 清空，再在同一事务里按源全量重写） |
| 按业务键 upsert | 源表全量 | 按业务键更新 / 插入（目标端多出来的行保留） |
| 按时间戳增量 | 水位之后的新增 / 变更行 | 按水位追加 / 更新（不清空目标表） |
| 仅追加 | 源表全量 | 直接插入，不去重 |

**实测（矛盾构造不出来）**

| 检查 | 结果 |
|---|---|
| 目标节点还有可选的「写入方式」卡 | **0 个** —— 只有只读块 + "由「同步模式」决定" |
| 「全量覆盖」模式下 | 「增量设置」「业务键」**整段置灰**、不可编辑 |
| 切到「按时间戳增量」 | 增量设置**解禁**；**水位列候选只有「提单时间」**（源表真实存在的列） |
| 切模式后 | 目标节点卡面**自动**变成「按水位追加/更新 · 批次 5,000」；跳过节点由"不写目标"变成**「会触发」** |
| 换源表 | 源卡 302,938 → **104,496 行**、映射 **22/22 → 31/31**、耗时 14 → **5 秒**、目标表跟着改名 |
| `window.__taskConsistency()` | **[]**（两次都为**空**；有矛盾时会返回具体条目并在控制台报错） |

> 这条要求同时是给真实实现的验收项：**任何两个节点不得各自持有同一配置项**；
> 面板候选值必须由服务端返回的元数据生成（源表的列、可作水位的列、可作业务键的列），
> **不允许前端硬编码**。

## 五、交付结果要求（验收标准）

> 这一节是我建议你**拿来卡验收**的清单。每条都可执行、可观察。

### 5.1 功能验收（必须全过）

1. 能新建一条同步任务，能从下拉里选到源/目标连接与表，字段映射能自动匹配且可手工调整
2. 三种模式各自可跑通：全量覆盖 / 按主键 upsert / 按时间戳增量
3. 「立即同步」与「试运行」都有；**试运行不得写目标库**（用只读连接验证）
4. 目标表不存在时，能按源结构自动建表（类型、长度合理）
5. 同步任务能作为**作业步骤**保存并执行；能挂到**定时任务**上按计划跑
6. 每次执行在运行日志里留下结构化记录（标签行格式，与今日定稿一致）
7. 失败时日志给出**人话原因**（连接失败 / 表不存在 / 主键冲突 / 类型不兼容），不直出英文驱动栈

### 5.2 数据正确性验收（最关键，逐条查库）

| 场景 | 期望 |
|---|---|
| 全量覆盖：源 1000 行，目标原有 500 行 | 目标**恰好 1000 行**，且与源逐行一致 |
| upsert：源改 3 行、新增 2 行 | 目标 **updated=3 / inserted=2**，总行数 +2，无重复主键 |
| 增量第一轮 | 全量拉取，水位推进到源表当前最大值 |
| 增量第二轮（源无变化） | **读取 0 行，目标不变，水位不倒退** |
| 增量第二轮（源改 1 行，时间戳更新） | 只读到那 1 行；**若该行时间戳未变则捕获不到——这是已知语义，必须在文档里写明** |
| 中途失败（模拟目标库断开） | **水位不推进**（下次可重跑），目标表不残留半批数据（事务）或明确标注"失败前已落盘 N 行" |
| 重复执行同一轮（幂等性） | 全量覆盖模式结果不变；upsert 模式不产生重复行 |

> ⚠️ **增量同步最大的坑已被实测证实**（§2.4）：源表没有"行修改时间"列，
> 而会变的列（订单状态 / 退款状态）的变动发生在**任意年龄**的行上（最久 1,498 天前）。
> 因此**这条验收项本身就是判定"某张表能不能用增量"的依据**：
>
> **验收用例（在测试库上，已有复现夹具）：**
> 1. 把 `dc_sync_src.订单表` 里一行**老订单**（`订单创建时间` 在 90 天前）的 `订单状态` 改成 `已取消`
> 2. 跑一次时间戳增量同步（水位设为 30 天前）
> 3. **预期：这一行不会被同步** → 这证明增量对"会变的列"无效
> 4. 对照：同一场景改用**全量覆盖**跑一次，**目标表必须与源表逐行一致**
>
> 夹具里已预置 20 行这种样本；实算结果是 **91 行本该同步的更新会被增量漏掉**。
> 这一步跑通，等于把"该用哪个模式"从**猜**变成**测**。

### 5.3 边界与异常验收

- 源表为空 / 源表有 NULL / 源表列类型与目标不一致 / 源表列名大小写不同 / 目标表列更多

## 六、明确不做的事（一期）

1. **不支持 MySQL 以外的数据库**（连接模块本身就先只支持 MySQL）
2. **不做多表 / 整库批量同步**（一次一条表，要批量就用作业编排多条同步步骤）
3. **不做双向同步 / 冲突合并**（单向源 → 目标）
4. **不做 DDL 差异同步**（只按数据自动建表/扩列，不改源表已有列的类型）
5. **不做删除同步**（源端删行，目标端默认不删——这是刻意的，避免误删；如需删除必须是显式选项，另开二期）
6. **不做实时 / CDC 同步**（只做定时批量）
