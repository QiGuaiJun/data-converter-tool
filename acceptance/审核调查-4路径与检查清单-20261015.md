## 一、对 4 个执行路径的可行性结论

> 评价维度：① 跑得起 ② 不引入未声明依赖 ③ 不污染 218 个已有 acceptance 产物 ④ 与现有测试/验收惯例一致。

| 路径 | 可达性 | 主要卡点 / 风险 | 推荐度 |
|---|---|---|---|
| **1. 新增 pytest 自动化用例** | ✅ 可达（最低风险） | 现有 7 个测试文件全部使用 **`tests/<name>.py` 直接 `import server`** 函数级模式（`test_jobs_schedule.py:28` `test_schedule_precheck.py:46` 等），零外部依赖；pytest 已在 `requirements-lock.txt` 中（`pytest==9.1.1`）；`tests/conftest.py` 仅做 sys.path 注入，无 Flask test client —— 不适合做 HTTP 端到端，但**适合"任务编辑→保存→执行"函数级回归**。"取消/失败恢复"涉及 HTTP 真实路径与前端 abort 行为，pytest 这一层**覆盖不到**（详见第二节 4.1）。 | ★★★★★ |
| **2. 新增 Playwright 验收脚本** | ⚠️ 可达，但**依赖未声明** | 仓库**没有** `package.json` / `node_modules`（已探测 `Test-Path` 双双为 False，`node -e "require('playwright')"` 返回 `MODULE_NOT_FOUND`）。`acceptance/ui_walkthrough.js:13`、`ui_replay.js:18`、`ui_replay_b.js` 都是 `require('playwright') + chromium.launch()`，依赖来自**全局 NODE_PATH 或手工 npm 装**。首次跑需 `npm install playwright`（含 chromium 二进制约 150MB，需联网）。一旦装好，模板齐备：UI 枚举、安全点击白名单、隔离端口（51979/51980/51981/51983）、截图证据目录模式均已在 `acceptance/V6-验收进展-20260919.md` 固化。 | ★★★★ |
| **3. 只审查现有代码并出报告** | ✅ 可达（最低动作） | 无任何依赖，可立刻开始。需关注的安全审阅读点：`server.py`（10174 行）、`public/jobs.js`（517 行取消按钮 = `dialog.close()`、618 行的 `saveJob`）、`public/connections.{html,js,css}`、`public/sync.{html,js,css}`、`public/styles.css` `public/theme*.css`。 | ★★★★ |
| **4. 审查后直接修复发现的问题** | ❌ 不推荐直接做 | 三重阻力：①改动会跨 server.py + 前端 js + css 多文件；②`acceptance/` 已固化 218 个 CSV / 71 个 LOG 产物（一动逻辑就触发"复跑不通过"，参见 `V6-验收进展-20260919.md` 第六节"3 条缺陷已修复并复验"的工作量级）；③没有 PR/CI/REVIEW 兜底（`pytest.ini` 仅 3 行，无 GitHub Actions / pre-commit）。除非先建评审流，否则**直接动手的回归成本不可控**。 | ★ |

### 1.1 落点建议

> **首选组合**：路径 1（pytest）+ 路径 3（代码审查）→ **覆盖检查清单第 4 项的 80%**。
>
> **补强**：路径 2（Playwright）→ **覆盖检查清单第 5、6 项**（视觉 / 兼容性）。
>
> **暂缓**：路径 4（直接修复）→ 留待评审机制到位、或先把"产品空白"与"测试缺口"两类问题切开，**先补缺失 API 再补测试**。

## 二、检查清单三维度对应的真实问题

### 4. 业务流程与状态管理

#### 4.1 已覆盖 vs 未覆盖（用证据说话）

| 子项 | 现有测试 | 评价 |
|---|---|---|
| 创建 → 编辑 → 保存 → 执行 | `tests/test_jobs_schedule.py:141` `test_saved_job_runs_successfully` 等 17 个 `def test_*` | ✅ 函数级 happy path 已有 |
| 返回 / 刷新 / 重新登录后保留 | — | ⚠️ **未覆盖**，但产品上 `imports.db` 持久化，无理由失败；属于"应当补但风险低" |
| 重复提交 | — | ⚠️ **未覆盖**；前端用 `requestJson` 包装 `fetch`，没有显式节流 / 去重逻辑 —— 需复核 `public/jobs.js` 的 `saveJob()` |
| **取消操作** | — | ❌ **产品功能缺失**（见 4.2） |
| **执行失败后恢复** | `tests/test_jobs_schedule.py:218` `test_compact_failure_reason_*` 只测**日志折叠**，**未测恢复路径** | ❌ **测试缺口** |

#### 4.2 ⚠️ 关键发现：产品端「取消正在运行的任务」**根本没有实现**

证据链：

1. `server.py` 全文 `grep`（`handle_job_cancel|cancel_job|abort_job|/api/jobs/.+/cancel|runs/cancel|jobCancel|/api/runs`）→ **0 命中**。
2. `public/jobs.js:517`：
   ```517:517:public/jobs.js
   $("#cancelJob").addEventListener("click", () => $("#jobDialog").close());
   ```
   ——"取消任务"按钮**仅关闭编辑对话框**，并不能取消已经 `run_saved_job()` 启动的作业。`#jobDialog` 是**编辑**模态框（保存前取消编辑的语义），不是**运行中止**按钮。
3. README 没有"取消运行中任务"的能力说明；V6 验收档（`acceptance/V6-验收进展-20260919.md`）230 条全过、0 不通过，**没有覆盖这条** —— 共识是"未交付"。

**结论**：检查清单第 4 条「取消操作」在产品端是**空缺口**。如果走"路径 1（pytest）"或"路径 2（Playwright）"，需要先决定：

- 选项 A：把"取消运行中任务"列为**新需求**，进入研发管线，先实现再测。
- 选项 B：暂时把这条从检查清单里**降级**为"已知未实现"，只测"取消编辑对话框后表单状态恢复"。`#jobDialog` 的关闭本身有 form 重置逻辑（`jobs.js` 中 `selectedJobId` `editingJobId` `draftSteps` 的作用域），这是值得测的薄壳。
- 选项 C：补一份 Playwright 用例专门证明"用户期望与产品行为不一致"，作为产品待办的证据。

#### 4.3 重复提交 / 失败恢复的检测入口（建议后续补）

| 子项 | 建议测试入口 |
|---|---|
| 重复提交 | 监控 `saveJob()` 的 fetch 调用次数（Playwright `page.on('request')`） |
| 失败后恢复 | 让某个 step 故意抛错（数据库连接断 / SQL 错误），看 `_job_run_steps` 表 status 字段、回滚、是否可重试 |
| 刷新保留 | 浏览器 F5 后 `imports.db` 数据完整性断言 |

### 5. UI 与交互体验

#### 5.1 资源结构概览

前端是**多页 + 同名 js 配对**：

- `index.html` / `export.html` / `connections.html` / `sync.html` / `query.html` / `tables.html` / `jobs.html` / `schedule.html` / `api.html` / `docs.html` / `feedback.html` / `audit.html` / `users.html` / `login.html`
- 公共壳：`shell.js`、`module-pages.js`
- 主题：`styles.css` `theme.css` `theme-classic.css` `connections.css` `sync.css` `sql-editor.css`
- 资产：`public/assets/`、`public/fonts/`、`public/icons/`（10 SVG + 7 PNG + 2 HTML）

#### 5.2 真实风险点（来自代码阅读）

| 风险 | 位置 | 性质 |
|---|---|---|
| `setStatus()` 在 `jobs.js:23` 用 **innerHTML 拼接转义后字符串，再用 `.replace` 注入 `<br>`** —— escape 函数没问题（`&<>"'` 全覆盖），但任何后续拼接若改成 `innerHTML = unescaped` 就会 XSS | `public/jobs.js:23-29` | 中风险 → 需 code review 看全部 `innerHTML` 调用 |
| `audit.html` / `users.html` 等管理页通常会显示用户输入，统一审计 html 注入 | 待复核 `audit.js`、`users.js` 的 `innerHTML` 调用 | 待审 |
| 多主题（`theme.css` + `theme-classic.css`）切换时若字体/间距不一致，会出现"换主题后错位" | `public/theme.css`、`theme-classic.css` | 中风险 → 需 Playwright 跨主题截图比对 |
| 图标有两套（`icons/*.svg` + `icons/*.png`），同一按钮可能被交替引用，搜索结果可能造成视觉不齐 | `public/icons/` | 低风险 |

#### 5.3 Playwright 能回答的 UI 问题

- 不同 viewport（1280/1440/1920/2560）下元素是否溢出 / 重叠。
- 加载 / 禁用 / 悬浮 / 选中态的 `getComputedStyle` 一致性。
- 按钮文字截断（中英文混排、32+ 字符长标题）。
- 同一控件在三个主题下的渲染 diff。

### 6. 兼容性

#### 6.1 现状

- 仓库**没有**浏览器分布声明、browserslist 配置、ESLint / Stylelint 配置（搜索 `browserslistrc`、`.browserslistrc`、`stylelint.config.*` 均未找到）。
- 前端 JS 大量使用 ES2020+（`Set` `Map` `?.` `??` `async/await` + fetch），CSS 用 `var()` 自定义属性 —— 这意味着 **IE 已不在目标内**。
- V6 验收档已用 Playwright 跑过 Chrome（Headless Chromium），**Edge 路径未单独验证**（Chromium 内核相同，但扩展行为不同）。

#### 6.2 Playwright 才能回答

- Chrome 最新稳定版、Edge 最新稳定版、`--enable-features=...` 下的兼容表现。
- 1440 / 1920 / 2560 三档 viewport 截图比对。
- 移动端 viewport（即便产品定位是桌面工具，「运维临时打开看报表」场景下手机适配也要点一下）。
- **跨域 / 同源策略**：Cookie 是 `HttpOnly`，HTTPS 下加 `Secure` —— 不同 `X-Forwarded-Proto` 头下 Cookie 是否生效需验证。

#### 6.3 当前阻塞项

| 阻塞 | 影响 |
|---|---|
| `node_modules` 不存在 | 无法直接 `require('playwright')` |
| 未声明浏览器版本 | Playwright 默认捆绑 Chromium，要测 Edge 需 `npx playwright install msedge`（约再下 100MB） |
| 没有 `package.json` | 需要先 `npm init` + 加 `playwright` 依赖 |

## 三、推荐执行顺序（自适应落地建议）

按"由低风险到高风险"递进：

### 阶段 1（≤ 1 小时，纯代码工作）

走 **路径 3（只审查并出报告）**。读完下列文件并产出"问题清单 v1"：

- `server.py`（重点：`/api/jobs/*`、`/api/schedules/*`、`/api/connections/*`、`public_auth_enabled()` 矩阵）

- `public/styles.css` + `public/theme.css` + `public/theme-classic.css`

**预期产出**：可立即落盘的"代码问题清单"（不修，只标）。

### 阶段 2（≤ 半日，零依赖）

走 **路径 1（pytest）**。新增 1 个文件：

- `tests/test_e2e_task_flow.py`（参考 `test_jobs_schedule.py` 的隔离模式：临时 DATA_DIR + `tracking_connect_db` 收尾）

覆盖：

- 创建 → 编辑 → 保存（断言 imports.db 写入）
- 同一作业重复 `save_job()`（幂等 vs 新版本，**回答检查清单的"重复提交"子项**）

- `#jobDialog` 关闭后 `draftSteps` `editingJobId` 重置（**回答"取消编辑后能否正确恢复"子项**）

### 阶段 3（半日，需装包）

### 阶段 4（明确范围再启动）

走 **路径 4（直接修复）**，**仅在以下条件同时满足时**：

- 阶段 1 + 2 + 3 的报告已沉淀到 issue 列表。

## 五、结论

1. **路径 1 + 3 是高 ROI 组合**：零依赖、能直接落盘、能覆盖检查清单第 4 项的多数子项。
2. **路径 2 是补全检查清单 5、6 项的唯一现实手段**，但需要在仓内首次声明 npm 依赖。
3. **路径 4 暂缓**：先把"产品空白"（4.2 取消）与"测试缺口"分离决策，避免改动炸开 218 个现有 acceptance 产物的口径。
4. **最关键的真实问题**：**「取消运行中任务」是产品空缺口**，**「执行失败恢复 / 重复提交 / 刷新保留」是测试空缺口**。这两类缺口不能混为一谈 —— 必须先确认产品是否要补，再决定测哪些。
