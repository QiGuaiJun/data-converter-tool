# 事故复盘：云端服务"假死"24 小时（2026-09-29 ~ 09-30）

> 状态：**已修复并验证**（提交 `dc4dfd5`）
> 影响：2026-09-29 上午 ~ 09-30 09:14（约 24 小时），云端 `https://81.70.230.116` 全部功能不可用；
> 本机桌面版不受影响。

## 1. 现象

云端访问不了。但**服务器本身一切正常**：

| 层 | 现象 | 判定 |
|---|---|---|
| SSH 22 | banner 81ms 返回 | 服务器活着 |
| nginx 80 | 秒回 `301 → https` | nginx 活着 |
| **443 → 应用** | **等满 60 秒返回 504 Gateway Time-out** | **上游不响应** |
| 应用端口 51978 | 从外网探测超时（只绑 127.0.0.1，正常） | —— |
| 应用进程 | `ps` 显示 **STAT=`Rsl`、%CPU 99.4、累计 CPU ≈ 运行时长** | **在烧 CPU，不是等 I/O** |
| 应用日志 | 最后一次写入停在 **09-23 11:49**，之后**一条错误都没有** | 静默假死 |

两条关键判据：
- **60 秒** 正好是 nginx 的 `proxy_read_timeout` 默认值 → 是"上游无响应"而非"nginx 故障"；
- `ps` 的 **STAT=`R`** 排除了"卡在磁盘 I/O"（那会是 `D`）。

## 2. 定位过程（值得复用）

1. **分层探测**把范围缩到应用层：22 有 banner、80 有 301、443 等满 60s 得 504。
2. `systemctl status` 看累计 CPU：**6d20h 的 CPU 时间 / 6d21h 的运行时长 ≈ 100%** ——
   说明它几乎全程占满一个核。
3. `ps -L -p <pid>` 看**线程**：主线程 `R` 独占全部 CPU，另两个线程 `futex_do_wait` 干等。
4. `py-spy dump --pid <pid>` 看**栈**：主线程停在
   `select → serve_forever → main`，**不在业务代码里** —— 于是怀疑 accept 循环空转。
5. 查 `/proc/<pid>/fd`：**1024 个（正好撞上 soft limit）**，其中 **1019 个是
   `/opt/dc/runtime/data/imports.db`**。根因锁定。

> 工具：`pip install py-spy` 后 `py-spy dump --pid <pid>`（只读 attach，不会杀进程），
> 是"进程活着但不知道卡在哪"时的第一选择。

## 3. 根因

```
sqlite3.Connection 的上下文管理器只管事务（提交/回滚），**不关闭连接**。
项目里 82 处 `with connect_db() as conn:` 因此每个触及数据库的请求泄漏一个句柄。
```

泄漏累积到 FD 上限后的连锁反应：

1. `accept()` 报 `EMFILE`（Too many open files）；
2. `socketserver.BaseServer._handle_request_noblock()` **静默吞掉**这个 OSError，
   只 `return`（**不打印任何东西**）；
3. 监听队列里的连接还在 → `select()` 持续报可读 → `serve_forever` **满速空转**；
4. 一个连接都服务不了、一条日志都不出；
5. nginx 等满 60s → 504。

**为什么 systemd 没救回来**：`Restart=always` 只在**进程退出**时触发。
进程真退出的话 nginx 会立刻回 502、systemd 5 秒后拉起 —— 反而不会被察觉；
而"卡住不退出"systemd 完全看不见，于是静默挂了 24 小时。

### 时间线还原

应用在 **09-23 11:49** 前后停止响应 —— 从 11:27:43 启动算起只有 22 分钟，
即约 1000 次数据库请求就把 1024 个句柄耗尽了（当时正值同事点击页面）。

## 4. 修复（四层）

| 层 | 措施 | 位置 |
|---|---|---|
| 根因 | `_ClosingConnection(sqlite3.Connection)`：`__exit__` 先走原事务语义再 `close()`；`connect_db()` 用 `factory=` 接上 —— **一处改动修好全部 82 个调用点**，事务行为不变 | `server.py` |
| 可观测 + 自愈 | `ResilientHTTPServer`：accept 失败不再静默 —— 打 WARNING（含 errno）、退避 0.2s、连续 100 次（约 20s）打印 FATAL 并 `os._exit(1)` 交给 systemd。**宁可重启，不要假死** | `server.py` |
| 外部看门狗 | 每 2 分钟探 `/api/ping`（超时 20s），连续 2 次失败 → **先存现场**（进程/内存/磁盘/日志）再重启，15s 后复核 | `deploy/dc-watchdog.sh` |
| 纵深防御 | systemd 单元 + drop-in `LimitNOFILE=65536` | `deploy/tencent-cloud-setup.sh` |

## 6. 教训

1. **"服务掉线"先分层探测再动手**。TCP 端口通 ≠ 应用可用；
   用 `curl -f` 加**长于 nginx `proxy_read_timeout` 的超时**，能把 502（进程没了）
   和 504（进程卡住）区分开。
2. **`Restart=always` 不是万能的**，它只处理进程退出。任何无人值守的服务都该配
   **外部健康检查 + 重启**的看门狗，并且**必须在重启前留现场**（否则永远查不出根因）。
3. **`with sqlite3.connect(...)` 不关闭连接**是个高频陷阱。要关闭就用
   `contextlib.closing(...)` 或像本项目这样用自定义 `factory`。
4. **库函数会静默吞异常**：`socketserver` 吞掉 accept 的 OSError，导致"零日志假死"。
   关键循环的异常要自己接住并打出来。
5. **FD 耗尽的排查动作**：`ls /proc/<pid>/fd | wc -l` 对比 `/proc/<pid>/limits`，
   再 `ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn`
   看是**哪一类**句柄在堆积 —— 这一步直接指认了 `imports.db`。
